INVESTIGATION OPENING
有一个反直觉的事实：在 DeepSeek Harness（dsh）里，不存在"聊天记录"这个一等公民。
你看到的那个聊天界面，是派生的。真正的数据本体，是一条 append-only 的事件日志。
这不是一个实现细节，这是整个框架的地基。理解了它为什么放弃"存消息"、选择"存事件"，你几乎就能理解它后面所有的设计决策。
这篇文章不讲功能清单，讲底层机制。我会沿着一条主线走：一个 agent 框架，怎么把"AI 替你干活"这件事，变成可回放、可审计、可恢复的数据。
EXHIBIT 01 事件溯源
地基：会话是日志，消息是投影
先说结论性的那句：dsh 的 Session 采用事件溯源。append-only 的日志是唯一真相源；模型看到的消息历史，是从日志里增量投影出来的视图。
为什么？因为"聊天记录"这个抽象撑不住 agent 的真实需求。agent 的会话里混着很多"不是消息"的东西：工具调用的开始、审批的问与答、turn 的边界、原始 token 流、压缩时刻、子代理的分叉点。这些东西一旦塞进扁平的消息模型，信息就丢了。
所以 dsh 把会话拆成了事件。每个事件还带着三个结构化字段：sourceEventSeqs 记录引用了哪些早先事件；surfaceOp 标记新增还是替换；ignorable 标记未知类型可否安全跳过——后者解决的是"日志格式会演进"这个现实问题。
这一步是理解后面一切的关键：日志是全部，消息是视图。
这个设计直接催生了四个能力，每一个对应一个真实痛点。
崩溃可恢复。按 id 恢复，turn 接着走。更妙的是崩溃修复语义：日志里有 tool/call 却没有结果时，恢复会合成 TOOL_OUTCOME_UNKNOWN，附风险提示——"是否重试取决于操作是否幂等，不要盲目重试"。它不替你猜，它把不确定性诚实地交给模型。
压缩不删历史。compaction 做的是 replace：追加新条目"遮住"旧节点，不删原始日志。压缩是为了省 token，不是为了毁证据。
分叉只在稳定边界。fork 只允许在"关闭的 turn"切分，保证被 fork 出去的历史是可独立成立的完整叙事。
请求可重建。每个 request/header 记录完整请求快照，事后能精确重建"当时模型到底收到了什么"。
EXHIBIT 02 驱动
整个框架只有一个循环，其余全是插件
dsh 里有一个包叫 dsh-agent-loop，文档里有一句话值得单独摘出来：这是整个 harness 里唯一包含具体循环逻辑的包。其余一切——沙箱、审批、压缩、持久化、子代理、UI——都是挂在这个循环周围的插件。
"驱动"一个 agent 是怎么回事？核心是一个统一的 send() 原语，带三个预设别名，对应三种输入方式：
followup()——追加到"下一轮"FIFO 并唤醒：最普通的"接着聊"。
steer()——追加到"下一步"inbox 并唤醒：插队式即时引导。
inject()——追加到"下一步"inbox 但不唤醒：静默注入，等 agent 因别的原因被唤醒时再用。
这三种语义区分了"排队等、插队催、塞进去但别吵醒"。而在 turn 边界，driver 会原子地"认领"输入——先发事件、再改投影，每个事件都可追溯。
还有一处体现"循环尽量薄"：模型调用成功后恰好锚定一条 assistant/message 完成事件——因为消息历史的权威来源必须落在日志里，而不是飘在某个执行栈上。栈会丢，日志不会。
EXHIBIT 03 工具
工具不是函数，是一条管线
每次工具调用都要穿过一条五段管线：pre-execute → 单调 guards → execute → post-execute → result。每个都是扩展点。三个细节体现功力：
门禁与 guard 是两回事。pre-execute 可拒绝可放行；而 guard 是单调的——只能拒绝，不可被翻案。把"可以商量"和"没得商量"分开，安全策略走后者。
作用域是分层的。全局工具层 vs agent 级 scope，可 shadow 可 restrict。同一个进程里，native agent 和 Code Mode agent 各看各的目录，互不干扰。
Code Mode 的权衡。模型写代码调工具，但中间值是执行局部、不落日志——刻意为之，代价是可回放性打折。应对是：每个子调用仍发成对事件，保住"调了哪些工具"的审计线索。这种"明确知道在哪一步做了权衡、并写进文档"的态度，最让人信服。
EXHIBIT 04 沙箱
沙箱不是"拒绝权限"，是"包装命令"
dsh 的思路更底层：confine(argv, policy) 返回一组包装后的 argv——"用这个替代你自己原来的命令"。包装后的进程连同它 spawn 的一切子进程，都跑在受限环境里。这是"进程沙箱"和"文件过滤"的本质区别：前者约束执行体，后者只拦文件访问。
三档：read-only / workspace-write / danger-full-access，策略跟着每次调用走。最硬的一条是失败关闭：平台没有可用后端，直接抛 SANDBOX_UNAVAILABLE，拒绝执行，绝不降级裸跑。
文档同样诚实：这个沙箱只管文件效应。网络、进程、syscall、设备、凭据都不在词汇表里。要容器、微 VM、远程执行，得换掉整个能力实现，而不是加 provider。这种"清楚说明自己不做什么"的诚实，在开源项目里相当稀缺。
升级权限也不是"把沙箱拨宽一档"，而是一次带理由的新请求，走人工审批，审批结果成对记录进审计。批了这一次，不批下一次。
EXHIBIT 05 扩展
三条缝，与一个被忽视的工程现实
单 agent 有天花板，dsh 用三条"缝"撑开它，三条缝遵循同一模式：接口定义与实现分离。
子代理缝——统一 API 委托子任务，provider 决定跑在本进程、另进程还是未来传输，调用方无感。
工作流缝——模型写编排脚本，扇出子代理分阶段并行，脚本只做协调。
目标缝——一个 agent 挂持久目标，跨轮推进，用 revision 做 compare-and-set 防呆。
真正让我觉得"认真做过工程"的，是工作流的失败纪律：fatal 错误逃逸出 parallel()/pipeline()；而子代理正常返回了非 completed 结果，不是故障——agent() 返回 null，让脚本自己处理。基础设施的错，和任务的正常失败，不是一回事。前者炸出来，后者交给编排逻辑。
最后说一个最容易被忽略的工程现实：KV cache 友好性。dsh 每个模块文档都有 "KV Cache effect" 小节。因为前缀缓存是真实成本：历史字节保持稳定，推理就能复用前缀。这就是为什么压缩要"遮住"而不是"重排"——重排会让整个后续全部失效。一个框架把"对 KV cache 的影响"当作每个功能的设计约束来记录，说明它想的不只是"能不能跑"，而是"跑起来贵不贵"。
回头看，dsh 的设计有一条清晰的主线：
会话做成事件日志，是为了可回放；循环做成唯一且薄，是为了可替换；工具做成管线加分层作用域，是为了可拦截；沙箱做成包装 argv 加失败关闭，是为了可约束；三条缝加 KV cache 记录，是为了可扩展且不失控的成本。
这些词——回放、替换、拦截、约束、成本——都不是模型的能力，是 harness 的职责。
FINDINGS
模型的强，会继续涨。
而 harness 决定了一件事：当 AI 在深夜替你干活，第二天早上，你能不能说清它干了什么、凭什么干、花了多少。
